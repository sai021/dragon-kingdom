# Developer guide: building and testing

> This guide describes the installed 0.2.4 prototype. For the new startup, parent
> authentication and update behavior, use the [0.3.0 candidate notes](NEXT-RELEASE.md).

Start here for firmware setup, S3/C3 builds, uploads and regression checks.
For related developer tasks, see [batch flashing](BATCH-FLASHING.md),
[hardware wiring](../dragon-firmware/HARDWARE-WIRING.md),
[architecture and API](ARCHITECTURE.md), and the current
[project checkpoint](PROJECT-STATUS.md).

Device setup Wi-Fi and browser access use the shared password `dragon123`;
the browser username is `parent`. This firmware replaces older random access
keys on boot without changing home Wi-Fi credentials, profiles or creations.

## Firmware toolchain

Install Python 3 and Arduino CLI on the development computer. From
`dragon-firmware`, run:

```sh
python tools/dev.py setup
python tools/dev.py build
python tools/dev.py ports
python tools/dev.py upload --port YOUR_PORT
python tools/dev.py monitor --port YOUR_PORT
```

On Windows, Python may be `py`; on Unix it may be `python3`. Use `--cli PATH`
if Arduino CLI is not on PATH. Setup installs Arduino-ESP32 3.2.1 and Adafruit
NeoPixel 1.12.5. The helper selects the ESP32-S3, USB hardware CDC, 4 MB flash,
2 MB PSRAM and custom partitions. It enforces the actual 0x180000-byte app
partition limit rather than trusting the compiler's generic flash percentage.

For the eight-pin-compatible C3 SuperMini, use `python tools/dev.py build --board c3`
or `python tools/dev.py upload --board c3 --port YOUR_PORT`. For upload with ROM
chip detection, use `python tools/dev.py upload --board auto --port YOUR_PORT`.
The default remains S3. Builds are isolated under `build/s3` and `build/c3`.
C3 uses 4 MB flash, DIO, hardware USB CDC and no PSRAM. Both targets retain
network-event locking, the same partition offsets and the saved-data schema.
The C3 pin map and outstanding physical checks are in [batch flashing](BATCH-FLASHING.md).

Do not upload to a port remembered from a prior session without checking its
current identity and wiring. Close monitors before uploading. Laptop USB and
external/main power must not be connected simultaneously in the present circuit.

## Editable sources

For multiple boards, use the [batch flasher](BATCH-FLASHING.md). It builds once
and provides a window for selecting and uploading to each board in turn.

- Palette catalog: `presets/dragons.json`, generated by `tools/palettes.py`.
- Phone UI: `web/dragon-kingdom.html` and `web/library.js`, embedded by
  `tools/embed_web.py` during every build.
- `DragonPresets.h` and `DragonWebPage.h` are generated and retained for
  inspecting the actual shipped code. Do not hand-edit them.
- `DragonPrototype/build_opt.h` must remain in the sketch so the network-event
  locking definition applies consistently to the networking libraries.

Catalog IDs depend on order. Preserve order or implement a saved-library
migration before changing it. Library snapshots are versioned binary records,
not cross-platform user backup files.

## Python and native regression checks

Use a C++17 compiler and Python with tkinter available:

```sh
python tools/run_tests.py
```

Use `--cxx PATH` for a compiler not on PATH, or `--zig PATH_TO_ZIG` for Zig's
C++ mode. The runner builds fifteen independent suites under ignored `.tools/`,
including the simulated C3 pin map, USB ceiling and sunrise scheduling/rendering.
USB network credential framing is checked separately.
The editor Python test uses Tk and needs a display. On Linux headless runners,
install tkinter/Xvfb and run `xvfb-run -a python tools/run_tests.py`.

Native tests substitute sensor/serial/storage fakes and exclude the Wi-Fi radio
adapter. They verify firmware logic, not the physical circuit or Wi-Fi stack.

## Phone-browser simulations

From `dragon-firmware`, install Node.js dependencies and a browser:

```sh
npm ci
npx playwright install chromium
npm run test:web
```

`tools/test_web.cjs` can also take a Playwright package path followed by an
optional browser executable. It has been run locally with a bundled Playwright
runtime and headless Edge. Tests use simulated HTTP responses at a 390×844
viewport; screenshots go to `.tools`. Do not present them as physical-phone
or ESP32 API verification.

## Prepared device and setup card

Install Python's `pyserial` for serial tools. Immediately after upload/reset:

```sh
python tools/capture_web_setup.py --port YOUR_PORT
```

This captures the boot setup line, writes local credentials and generates a
printable card under `.tools`. Its log redacts the password. Never commit the
card/credential capture. Parents should receive the card, not coding tools.

## USB hardware diagnostics

At 115200 baud with native USB CDC DTR enabled and RTS inactive, `status`,
`sensors` and `power status` report the real runtime and startup ADC evidence.
`wifi status` reports connection state, IP and hostname without a password.
`wifi setup` reopens setup Wi-Fi without deleting saved home credentials.
`wifi scan` starts an asynchronous 2.4 GHz scan; repeat it for results. Results
contain hex-encoded network names, RSSI, channel and security mode, so raw
captures should stay in ignored output. Status includes the last ESP-IDF
disconnect reason and whether a join is still pending.
`wifi join HEX_SSID HEX_PASSWORD` provisions via USB (use `-` for an open
network). Encode the UTF-8 bytes as hexadecimal; do not put credentials in
committed scripts, command-line arguments or shared logs. Responses do not
echo credentials. Home settings are saved only after a successful connection,
using the same save-on-success path as the browser. USB access is a trusted
physical developer interface. Keep all raw serial captures and NVS backups
under ignored `.tools/`. External/main power must remain disconnected.

For guided USB provisioning, run `python tools/provision_wifi.py --port YOUR_PORT`.
The password prompt is hidden. Automation may supply `--credentials-file` with
an ignored local JSON file containing `ssid` and `password`; there is deliberately
no password command-line option. The helper confirms connection and saved
configuration only after the pending join has completed. `alarm preview`,
`alarm status` and `alarm stop` exercise the sunrise over USB without network
access. The same 400 mA estimated USB ceiling applies.
`alarm disable` stops the sunrise and saves the daily alarm as disabled;
`alarm stop` only cancels the current occurrence.

For supervised low-light measurements, USB serial `testglow 1` through
`testglow 10` temporarily applies that raw percentage to the already session-
limited frame. It bypasses automatic/manual dimming and the one-count visibility
floor so integer-output extinction can be observed. It never increases the
session ceiling or saves a profile/setting. `testglow 0` ends the test; normal
brightness, dragon, touch and web play controls also cancel it. Status reports
the test percentage, nonzero pixel count and channel sum, not measured light or
electrical current. Restore normal brightness and `auto on` after testing.

Wi-Fi transmit power is limited to 8.5 dBm by
`Config::WIFI_TX_QUARTER_DBM` (34 quarter-dBm units), reapplied when starting
a station connection. On the USB-powered S3, a Wi-Fi-only comparison at this
setting joined the Slate Plus after default-power attempts repeatedly missed
802.11 authentication acknowledgements. This is a measured connection outcome,
not proof of a power-supply fault. Full S3 firmware joined and reconnected
after reset at this setting. Deployed range and C3 radio behaviour still need
separate physical checks. Do not increase the 400 mA estimated USB lighting
ceiling to compensate.

## Sunrise alarm and clock

`SunriseAlarm.h` contains the portable daily schedule, DST rules and monotonic
ramp/hold state machine. `AlarmWeb.h` registers authenticated `/api/alarm` GET/POST,
`/api/alarm/clock`, `/api/alarm/preview` and `/api/alarm/stop` POST routes.
Alarm settings use a separate checksummed `dragon-alarm/settings` NVS record;
existing library and Wi-Fi schemas are unchanged. Phone time-zone transitions
cover the next 400 days, including DST. A clock outside those rules waits for
phone sync. Settings are persisted only on Save; page-open sync updates RAM.
UTC is obtained from the phone and optionally NTP on home Wi-Fi. There is no
battery-backed RTC: offline restarts require opening the page again. A DST
gap skips a nonexistent wake-up time; repeated fall-back times fire once.
An active sunrise uses monotonic elapsed time, holds for 30 minutes and is
cancelled by normal play/touch controls. Preview ramps for 30 seconds and holds
for ten. The sunrise bypasses manual sleep and ambient gain, while retaining
the channel/current/USB ceilings and startup-failure indications.


## Release checklist

The printable manual is maintained in `docs/USER-MANUAL.md`. With Python's
`reportlab` installed, regenerate it from the repository root using
`python dragon-firmware/tools/build_user_manual.py`. The PDF is written to
`output/pdf/dragon-kingdom-user-manual.pdf`; render and visually inspect all
pages after editing it. It contains the documented shared access password, but no private household
Wi-Fi credentials or per-device setup captures.


1. Pass regression suites, browser simulations and firmware build.
2. Review generated headers for intentional source changes.
3. Validate staged files: no `.tools`, credentials, build products or large
   duplicate meshes/archives.
4. Record physical evidence separately from simulated checks.
5. Complete the actual-phone, persistence, touch-gesture and power checks in
   PROJECT-STATUS.md before a family release.
6. Review later STL, photos and Gerbers as a distinct hardware revision.

## Beta 8 night range

Automatic room-light gain uses permille precision, separate from the saved 0/10..100 Glow value. Ten ADC bins retain the existing filtering, hysteresis and dwell; their gain table is 15, 25, 50, 90, 150, 250, 400, 600, 800, 1000 per thousand of the already power-limited frame. For an otherwise full 204/255 channel at Glow 100%, the digital outputs are 3, 5, 10, 18, 30, 51, 81, 122, 163 and 204 (about 1%, 2%, 4%, 7%, 12%, 20%, 32%, 48%, 64%, 80% of 255). These are digital drive levels, not measured optical brightness or an absolute minimum on every artwork pixel.

Order remains artwork/80% channel cap -> session current limiting -> room-light gain -> selected Glow. Lower power, artwork colours and selected Glow can reduce output further. Existing one-count visibility protection keeps an awake pixel lit; black and Sleep remain black. Sunrise retains its independent ramp. The ambient gain fades by up to 10 permille every 30 ms, settling exactly at the target; ADC reads remain 4 Hz. No calibration/profile schema changes are needed. Serial reports `light_gain_permille`; the parent support export reports automaticLight, ambientGainPermille, roomLightStep and glowPercent.


## Beta 9 low-light colour

After the session current cap, ambient and selected Glow gains are multiplied before a single nearest-rounded RGB scaling. The prior two truncations lost weaker components and the old all-zero fallback selected one dominant channel (red on a tie). A dim neutral RGB(20,20,20) could therefore become RGB(1,0,0).

The new minimum keeps each nonzero input channel that is at least half its peak at one count. RGB white stays white and RG yellow stays yellow; weak accents are not automatically promoted. The fixed significance mask and nearest rounding are symmetric under RGB permutation and monotonic in gain, preserving the current limiter's binary-search requirement. Zero gain, intentional black, the 80% channel ceiling, USB 400 mA ceiling and startup/current policy remain intact. If the current budget cannot fund the multichannel floor, the current cap wins. Sunrise and raw bench diagnostics retain their own scaling.

The beta-8 table above records its truncation. With beta 9 nearest rounding, an otherwise full 204/255 channel at Glow 100% yields 3, 5, 10, 18, 31, 51, 82, 122, 163, 204 across the same ten ambient bins. At one or a few counts, some colour ratios are inherently unrepresentable in 8-bit PWM: this removes a software red bias, not a measured LED white balance. No temporal dithering, guessed channel calibration, saved-data migration or artwork changes are introduced.
