# Signed update contract and transition

Local beta 4 development is based on beta 3 at `7b0d9dc`, not the beta-2-based
shipping stable `v0.3.0`. Hardware and the public RSA trust root are unchanged.
No release or hosted asset was changed by this work.

## Format 2

Online manifests and offline packages sign these exact ASCII, newline-terminated
fields, in order: `dragon-update-v2`, board (`s3`/`c3`), firmware tag, decimal image
size, lowercase image SHA-256, decimal capability mask, decimal saved-data schema.
The next manifest line is the lowercase 256-byte RSA signature as 512 hex digits.
Offline JSON contains format=2, tag, capabilities, schema, board, size, sha256,
signature and the hex image. RSA-2048 PKCS#1 v1.5/SHA-256 and the existing public
key remain unchanged. Full image hash and ESP image validation still gate boot.

Capability bit 1 means chip-bound voltage calibration is read before startup power
validation. The device requires it whenever a valid chip-bound calibration record
is present (including a 1.000 correction). Schema 1 covers the unchanged library,
alarm, rotation, light-settings and backup layout. Other schemas are rejected;
future schema changes require a deliberate migration design, not a tag bump.
All compatibility/signature checks happen before `esp_ota_begin`.

Normal upgrades require a strictly newer vMAJOR.MINOR.PATCH[-beta.NUMBER] tag.
Equal/older versions are not normal upgrades. Stable sorts after its beta tags,
but capabilities and schema are independent gates. A stable tag alone cannot
permit loss of calibration. A parent can explicitly select **Return to Release**
for a compatible stable version, including an equal/older version. Checking a new
channel or intent requires another check; installation uses the checked intent.
Offline packages use the same explicit intent. Missing/v1 metadata is rejected.

USB recovery requires a signed release-set contract covering source commit,
source fingerprint, firmware tag, toolchain, capability/schema, both boards and
all bootloader/application/partition hashes. USB requires calibration capability
for every board, conservatively protecting a unit whose calibration cannot be
queried. Current supported installed releases use schema 1; do not use this tool
on a future/custom schema without a separately reviewed migration. A newer-than-
selected Auto device is refused, not stamped as the selected production version.

## Existing installed firmware: explicit bridge

Stable v0.3.0 and beta 1-3 cannot parse format 2 and cannot enforce this new policy.
Do not simply replace their update feeds with v2-only manifests and assume they
upgraded. Do not offer beta-2-based stable to the corrected C3.

After physical acceptance, produce a deliberately named **offline v1 bridge** of
this same calibration-aware beta 4 application, using the existing external key:

    python tools/sign_update.py sign --legacy-bridge --key PRIVATE_KEY_PATH --tag v0.3.0-beta.4 --board c3 --image build/c3/DragonPrototype.ino.bin --output .tools/bridge/dragon-c3-bridge.dragon.json

Repeat for S3. The v1 signature binds board/size/hash; the operator must independently
check bridge version and calibration support, since old firmware cannot. Install
through the older webpage, reload after startup, then use v2 packages thereafter.
Alternatively use the signed USB bundle with NVS-preserving recovery. No private
key is discovered or generated by ordinary preparation. No bridge was signed or
published during this work. Keep a matching bridge download available for older
customers; new firmware rejects it and therefore cannot downgrade through v1.
The publisher must coordinate old-format feeds, explicit bridge instructions and
new-format feeds; that publication remains separately authorized.

## Reproducible preparation

Install `requirements-test.txt`, run generated-source, Python/native/browser checks,
and build both boards with `tools/dev.py build --board s3` and `--board c3` using
Arduino ESP32 3.2.1 and NeoPixel 1.12.5. Commit the reviewed firmware/tool sources,
then rebuild both targets so provenance records that commit and fingerprint.

    python tools/prepare_release.py --tag v0.3.0-beta.4 --key PRIVATE_KEY_PATH --output .tools/releases/v0.3.0-beta.4

The output must not exist. The tool checks the installed public key, source tag,
clean tracked firmware sources, fresh build provenance, both targets, hashes and
two-slot partition layout. It produces signed offline/online assets and the signed
USB set without a board or network publication. Missing/stale build provenance is
an error, not permission to package cached binaries. Preserve accepted bundles
unchanged. Reproducibility here means recorded inputs and verified outputs; it
does not claim bit-identical builds across different host/toolchain installations.
